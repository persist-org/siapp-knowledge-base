# 04: Media and attachments

**Purpose:** Photo uploads. Used by selfie attendance, reports, instructions, patrol scans, panic reports, asset reports and E-Memo.

**Manual refs:** §2.6.2, §2.7.5, §2.8.5, §3.2.3.1 ("Foto tersebut hanya dapat diambil secara langsung"), §3.2.6.1.

**Needs:** 01.

**Contract changes:**
- The contract has no upload endpoint; its create inputs take `photos` as URIs.
  - Add `POST /media`, `POST /media/{id}/upload-url` (a new URL for a photo still `PENDING`, because an idempotent replay of `POST /media` returns the first, possibly expired, URL) and `POST /media/{id}/complete`.
  - Add `media_ids: int64[]` to every create input that has `photos`.
  - Document that `photos` in responses are short-lived signed URLs.
- Add `PUT /media/blobs/{token}` and `GET /media/blobs/{token}`, marked "only when the server stores files itself (`STORAGE_DRIVER=local`)". Clients never build these URLs: they use the `upload_url` and view URLs they are given.
- PR to `persist-ecosystem` in Phase 04.1.

**Error reasons:**
- `MEDIA_NOT_FOUND`
- `MEDIA_TYPE_NOT_ALLOWED`
- `MEDIA_TOO_LARGE`
- `MEDIA_NOT_UPLOADED`
- `MEDIA_ALREADY_ATTACHED`
- `MEDIA_PURPOSE_MISMATCH`
- `MEDIA_LIMIT_EXCEEDED`
- `MEDIA_URL_INVALID` (local driver only: a blob URL that is tampered with, expired, or used with the wrong type or size)

**Design**
- **Storage is chosen by `STORAGE_DRIVER`**: `local`, `minio` or `s3`. The client flow is the same for all three: register, PUT the bytes to `upload_url` with `upload_headers`, complete. The app never knows which driver is behind it.
  - `local` is the disk of **whatever machine the API runs on**, with no extra service. On a developer's laptop that is a folder in the project (`make run`). On a server it is a folder of that server, mounted into the containers. The same code and settings shape serve both; only `STORAGE_LOCAL_DIR` and `MEDIA_PUBLIC_BASE_URL` differ.
- With `minio` and `s3`, files go **straight from the device to object storage** through presigned URLs, and the API never proxies file bytes. With `local` the server *is* the storage. Bytes then go to a dedicated blob route that works like a presigned URL: no bearer token, a signed and expiring URL, and its own size cap. No other route ever receives file bytes.
- Capture metadata (time, GPS, source) is stored as anti-fraud evidence.
- ⚠ Every object key starts with the organization id, and every read is authorized by the owning record inside `WithTenant`. Comment why both: the key prefix keeps tenants apart in storage and in lifecycle rules (and, for `local`, in directories); the record check is what actually authorizes a viewer.

## Phase 04.1: Storage drivers and upload flow

**Goal:** A client registers an upload, uploads it to whichever storage the environment configures, and confirms it.

**Build**
- **`pkg/media/storage.go`**: the `Storage` interface: `PresignPut`, `PresignGet`, `Head`, `Delete`. Feature code depends on the interface only.
  - `NewStorage(cfg)` picks the driver from `STORAGE_DRIVER`. ⚠ Comment that `minio` and `s3` are the same driver with different defaults, so there are two implementations, not three.
  - At start-up (API and worker) the driver checks that it can work: `HeadBucket` for S3, or a write-and-delete probe in the directory for local. A wrong bucket, wrong keys or an unwritable directory then fail the boot, not the first upload.
- **`pkg/media/s3.go`: `S3Storage`**, used by `minio` and `s3`. It is the only file that imports the AWS SDK (aws-sdk-go-v2).
  - `minio` requires `S3_ENDPOINT` and forces path-style.
  - `s3` uses the AWS endpoint of `S3_REGION` unless `S3_ENDPOINT` is set, with virtual-hosted style.
  - ⚠ `S3_PUBLIC_ENDPOINT` (optional) is the host presigned URLs are signed for. Comment why: inside compose the API reaches MinIO as `http://minio:9000`, but a phone cannot resolve that name. Presign with the public host and talk to the API-side host for `Head`/`Delete`.
- **`pkg/media/local.go`: `LocalStorage`**, used by `local`.
  - Files live under `STORAGE_LOCAL_DIR`, at the object key. ⚠ Keys are generated by the server and checked against the key pattern. The resolved path must stay under the root (`filepath.Rel` check). Comment that this is what stops path traversal, even though no key ever comes from a client.
  - `PresignPut` / `PresignGet` return `{MEDIA_PUBLIC_BASE_URL}/api/v1/media/blobs/{token}`. The token is an HMAC-SHA256, keyed by `STORAGE_LOCAL_SIGNING_KEY`, over: the operation (put or get), the key, the content type, the maximum size and the expiry. Verification is constant-time. A put token cannot be used to read, and the reverse.
  - **`PUT /media/blobs/{token}`**:
    - checks the signature and the expiry;
    - requires the signed `Content-Type`;
    - caps the body at the signed size (`http.MaxBytesReader`, outside the API's 1 MB JSON cap);
    - writes to a temp file in the same directory, then fsyncs and renames. ⚠ Comment why: an interrupted upload never leaves a partial object that `complete` could accept.
  - **`GET /media/blobs/{token}`** serves the file with `http.ServeContent`, the signed content type, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, and `Cache-Control: private` no longer than the token's lifetime.
  - `Head` returns the size from `os.Stat`, and the type from sniffing the first 512 bytes (`http.DetectContentType`) rather than trusting what the client sent. `Delete` ignores a file that is already gone, like S3.
  - ⚠ The request logger redacts the token in `/media/blobs/` paths: it is a credential for as long as it lives.
  - ⚠ Comment the deployment rule: the API and the worker must see the **same directory**, so `media:cleanup` can delete. That means one host, or a shared volume. Backups of the directory are the operator's job, since nothing replicates it.
- **Config** (`pkg/platform/config`), checked at start-up like `JWT_SECRET`:
  - `STORAGE_DRIVER`: `local` | `minio` | `s3`. Default `local`. Anything else fails the boot.
  - `local`:
    - `STORAGE_LOCAL_DIR` (default `./data/media`; `/var/lib/siapp/media` in the image). It is created at start-up if missing. A relative path is relative to the working directory, and is resolved to an absolute path once, at boot, and logged;
    - `STORAGE_LOCAL_SIGNING_KEY` (required, at least 32 bytes, the same placeholder check as `JWT_SECRET`, never logged);
    - `MEDIA_PUBLIC_BASE_URL`: the API's origin **as the device sees it**. It defaults to `http://localhost:8080` in `development` and is required in `production`.
      - ⚠ Comment the local-dev catch: `localhost` on a phone is the phone itself. An Android emulator needs `http://10.0.2.2:8080`, and a real phone on the same Wi-Fi needs the laptop's LAN address (for example `http://192.168.1.10:8080`).
      - On a server it is the public HTTPS origin behind the proxy (for example `https://siapp.example.com`).
  - **The two `local` setups**, both documented in `.env.example` and `docs/dev-setup.md`:

    | | Laptop (`make run`) | Server (containers) |
    |---|---|---|
    | `STORAGE_LOCAL_DIR` | `./data/media` (in the repo, git-ignored) | `/var/lib/siapp/media`, a bind mount of a host folder such as `/srv/siapp/media` |
    | `MEDIA_PUBLIC_BASE_URL` | `http://localhost:8080` / `http://10.0.2.2:8080` / LAN IP | `https://<public host>` |
    | Shared by API and worker | same folder, same machine | same mount in both containers |
  - Add `data/` to `.gitignore`, so uploaded photos are never committed.
  - `minio` / `s3`:
    - `S3_ENDPOINT`;
    - `S3_PUBLIC_ENDPOINT`;
    - `S3_REGION`;
    - `S3_BUCKET` (default `persist-media`);
    - `S3_ACCESS_KEY` and `S3_SECRET_KEY`, both required and never logged;
    - `S3_FORCE_PATH_STYLE` (optional override of the driver's default).
  - Only the chosen driver's variables are required.
  - `.env.example` documents all three drivers, with `local` active, so a fresh clone stores photos on the laptop with nothing else running. The `minio` block is there, commented, for trying the S3 path; `make up` keeps running MinIO for that and for the tests.
  - `docker-compose.yml` (`app` profile): a `media-data` volume mounted at `/var/lib/siapp/media` in both `api` and `worker`, owned by the image's non-root user. The server deployment notes replace it with a bind mount of a host folder, so the files survive the containers and can be backed up.
- **Table `media`** (tenant table, RLS)
  - `id`, `organization_id`, `owner_personnel_id`
  - `purpose` ENUM(`PROFILE_PHOTO`,`ATTENDANCE_SELFIE`,`REPORT`,`INSTRUCTION`,`PATROL_SCAN`,`PANIC_REPORT`,`ASSET_REPORT`,`EMEMO`)
  - `content_type`, `size_bytes`, `storage_key`
  - `status` ENUM(`PENDING`,`UPLOADED`)
  - `captured_at`, `capture_latitude`, `capture_longitude` (all nullable)
  - `capture_source` ENUM(`CAMERA`,`GALLERY`,`UNKNOWN`)
  - `attached_entity_type`, `attached_entity_id` (both nullable)
  - timestamps
  - Index on (`organization_id`, `status`, `created_at`), used by the cleanup job.
  - The driver is **not** stored per row: one environment uses one storage. Moving between drivers is a copy of the objects under the same keys, done by the operator. Comment this.
- **`POST /media`** (idempotent, so an offline media queue can retry it)
  - Request: `{ purpose, content_type, size_bytes, captured_at?, latitude?, longitude?, capture_source }`.
  - Response: `{ id, upload_url, upload_method, upload_headers, expires_at }`. `upload_method` is always `PUT`. It is in the response so a future driver (for example a presigned POST) does not need an app release.
  - Allowed types: `image/jpeg`, `image/png`, `image/webp`. Max size 10 MB.
  - Storage key: `{organization_id}/{purpose}/{yyyy}/{mm}/{id}-{random}`.
- **`POST /media/{id}/complete`**
  - Owner only.
  - Calls `Head` to check that the object exists and that its size and type match, then sets status `UPLOADED`.
  - If the check fails, returns `MEDIA_NOT_UPLOADED`.

**Tests**
- **Storage conformance** (`pkg/media/storagetest`): one suite of put, get, head, delete, delete-missing, an expired URL, and a key outside the prefix. It runs against `LocalStorage` (always, in a temp dir) and `S3Storage` against MinIO (in `make test`).
- **HTTP flow**, run once per driver (`local` and `minio`):
  - register → PUT to `upload_url` → complete → status is `UPLOADED`;
  - complete without an upload fails;
  - a wrong type or an oversize file is rejected;
  - another person cannot complete someone else's upload;
  - cross-tenant: org B gets 404 for org A's media id;
  - an idempotent replay of `POST /media` returns the same id.
- **Local blob route:**
  - a tampered token, an expired token, a get token used for put, a wrong `Content-Type`, and a body over the signed size are all refused with `MEDIA_URL_INVALID` (413 for the size);
  - an upload cut off halfway leaves no file;
  - a file that is not an image but was declared `image/jpeg` fails `complete`;
  - the token never appears in the request log.
- **Config:**
  - An unknown driver, a missing variable of the chosen driver, and a short or placeholder signing key each fail `config.Load`. The other drivers' variables are not required.
  - With `local`, `MEDIA_PUBLIC_BASE_URL` defaults to `http://localhost:8080` in `development` and fails the boot when missing in `production`.
  - A relative `STORAGE_LOCAL_DIR` resolves to an absolute path, and a missing folder is created.

## Phase 04.2: Attach, signed reads and cleanup

**Goal:** Feature modules attach uploaded media to their records and return viewable URLs.

**Build**
- **`media.Service.Attach(ctx, q *db.Queries, AttachInput{ MediaIDs, OwnerID, Purpose, EntityType, EntityID, Max })`**
  - Exported and documented. It runs inside the caller's tenant transaction.
  - ⚠ Attach every item with one conditional `UPDATE … WHERE id = ANY($1) AND owner_personnel_id = $2 AND status = 'UPLOADED' AND purpose = $3 AND attached_entity_id IS NULL`, then compare the affected row count to `len(MediaIDs)`.
    - Comment why: this avoids a race where two records attach the same file.
    - If the count is short, re-select to report the exact reason.
  - `Max` defaults to 5.
- **`media.Service.Views(ctx, q, entityType, entityID, ids) ([]View, error)`**
  - Only photos attached to that very record are returned, so a module that passes ids straight from a request cannot show another record's photos.
  - Returns `View{ ID, URL (Storage.PresignGet, 1 h), ContentType, CapturedAt, CaptureSource }`. These fill the contract's `photos` arrays. The URL is a presigned S3 URL or a local blob URL, depending on the driver.
  - ⚠ There is **no** authenticated read endpoint by media id. The owning module authorizes access to its own record, then embeds these views. Comment this design choice.
- **Periodic task `media:cleanup`** (asynq, hourly, per organization)
  - For media that is `PENDING`, or not attached 24 h after creation: delete the object through `Storage.Delete`, then the row. The same code serves every driver.
  - Never delete attached media.
  - With `local`, it also removes temp files of abandoned uploads older than 1 h.
- Profile photos are **not** stored here: they come from Personel (`personnels.photo_url`). Remove the first plan's `PUT /me/photo`.

**Tests**
- Unit tests for `Attach` against the test DB:
  - happy path;
  - media owned by someone else;
  - media that is not uploaded;
  - wrong purpose;
  - already attached;
  - over the limit.
- HTTP tests, per driver:
  - the cleanup handler removes an orphan (its object too) and keeps attached media;
  - the job for org A never touches org B's media.
